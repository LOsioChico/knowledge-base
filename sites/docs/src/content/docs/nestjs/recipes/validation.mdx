> Validate bodies, query strings, and route params with one global pipe and declarative DTO classes. Same `class-transformer` / `class-validator` pair as [[nestjs/recipes/serialization|response serialization]].

<Aside type="tip" title="Prerequisites">
Before diving into this recipe, make sure you understand:
- [[nestjs/fundamentals/pipes|Pipes]]: since validation in NestJS is built on the Pipes architecture.
- [[nestjs/recipes/serialization|Response Serialization]]: since the same `class-transformer` / `class-validator` metadata pairs govern both validation and serialization.

## When to reach for it

- You assumed `body.email` was a string and it wasn't.
- Callers must not slip extra fields past your rules (`isAdmin: true` on signup).
- Query params arrive as strings but handlers want numbers.
- Create vs update need different rules on the same DTO shape.

## Setup

<Steps>

1. **Install `@nestjs/common` peer validation packages**: Install the required validator and transformer packages, verifying that the package installer exits successfully:

   <PackageManagers pkg="class-validator class-transformer" pkgManagers={['npm', 'pnpm', 'yarn', 'bun']} />

   *Verification: Verify that `class-validator` and `class-transformer` are listed in your `dependencies` block in `package.json` before registering the pipe.*

2. Register a global pipe in `main.ts` (secure defaults):

   ```typescript title="main.ts"
   import "reflect-metadata";
   import { NestFactory } from "@nestjs/core";
   import { ValidationPipe } from "@nestjs/common";
   import { AppModule } from "./app.module";

   async function bootstrap() {
   const app = await NestFactory.create(AppModule);
   app.useGlobalPipes(
   new ValidationPipe({
   whitelist: true,
   forbidNonWhitelisted: true,
   transform: true,
   transformOptions: { enableImplicitConversion: true },
   }),
   );
   await app.listen(3000);
   }
   bootstrap();
   ```

3. Define a DTO and use it on a handler (next section).

</Steps>

<Aside type="caution" title="Need DI inside the pipe?">

`useGlobalPipes(new ValidationPipe(...))` builds the pipe **outside** the container. For `ConfigService`, loggers, or request scope, use `APP_PIPE`: [[nestjs/fundamentals/global-providers|global enhancers]].

</Aside>

## First DTO (show the 400)

```typescript title="create-user.dto.ts"
import { IsEmail, IsString, MinLength } from "class-validator";

export class CreateUserDto {
  @IsEmail()
  email: string;

  @IsString()
  @MinLength(8)
  password: string;
}
```

```typescript title="users.controller.ts"
import { Body, Controller, Post } from "@nestjs/common";
import { CreateUserDto } from "./dto/create-user.dto";

@Controller("users")
export class UsersController {
  @Post()
  create(@Body() dto: CreateUserDto) {
    return { ok: true, email: dto.email };
  }
}
```

`POST /users` with a valid body:

```json
{ "email": "a@b.c", "password": "hunter2!" }
```

```json
{ "ok": true, "email": "a@b.c" }
```

Invalid input:

```json
{ "email": "not-an-email", "password": "short" }
```

`400 Bad Request`:

```json
{
  "statusCode": 400,
  "message": [
    "email must be an email",
    "password must be longer than or equal to 8 characters"
  ],
  "error": "Bad Request"
}
```

## `whitelist` + `forbidNonWhitelisted`

<Tabs>
  <TabItem label="Strip unknown fields">
    `whitelist: true` only: extra keys are removed silently.

    Request:

    ```json
    { "email": "a@b.c", "password": "hunter2!", "isAdmin": true }
    ```

    Handler receives:

    ```json
    { "email": "a@b.c", "password": "hunter2!" }
    ```
  </TabItem>
  <TabItem label="Reject unknown fields">
    Add `forbidNonWhitelisted: true`: same request returns:

    ```json
    {
      "statusCode": 400,
      "message": ["property isAdmin should not exist"],
      "error": "Bad Request"
    }
    ```
  </TabItem>
</Tabs>

Use **both** in production. Strip-only is for migrations where old clients still send deprecated fields.

<Aside type="caution" title="Without whitelist, mass-assignment is real">

`Object.assign(user, dto)` on an un-whitelisted DTO is how `isAdmin: true` reaches the database. The pipe default allows unknown properties until you flip the switch.

</Aside>

## `transform: true`

Without it, `@Body() dto: CreateUserDto` is a plain object: `dto.fullName()` throws if the DTO defines methods.

With `transform: true`, the pipe runs `plainToInstance` so decorators and instance methods work. The pipe only validates when the parameter **metatype** is a custom class ([`validation.pipe.ts`](https://github.com/nestjs/nest/blob/master/packages/common/pipes/validation.pipe.ts)); primitives still get coercion via `transformPrimitive`.

With a global `ValidationPipe({ transform: true })` registered and the following controller handler:

```typescript title="items.controller.ts"
import { Controller, Get, Query } from "@nestjs/common";

@Controller("items")
export class ItemsController {
  @Get()
  findAll(@Query("page") page: number) {
    return { page };
  }
}
```

A request of `GET /items?page=abc` returns a successful response containing `NaN` coerced to `null`:

```json
// GET /items?page=abc
// Response: 200 OK
{
  "page": null
}
```

(`JSON.stringify(NaN)` → `null`.) Prefer `@Query("page", ParseIntPipe)` when bad input should be `400`: see [[nestjs/fundamentals/pipes|Pipes]].

`enableImplicitConversion: true` (in `transformOptions`) coerces whole query objects: `?limit=10` becomes number `10` for `@IsInt()` instead of failing on string `"10"`.

### Query string validation and implicit conversion

Query parameters always arrive in the HTTP request as strings (e.g. `?limit=10&page=2`). To validate and coerce them into actual numeric values within a custom query DTO, use a combination of `@IsInt()`, `@IsOptional()`, and the `enableImplicitConversion: true` option:

```typescript title="dto/pagination-query.dto.ts"
import { IsInt, IsOptional, Max, Min } from "class-validator";

export class PaginationQueryDto {
  @IsOptional()
  @IsInt()
  @Min(1)
  page?: number = 1;

  @IsOptional()
  @IsInt()
  @Min(1)
  @Max(100)
  limit?: number = 10;
}
```

```typescript title="items.controller.ts"
import { Controller, Get, Query } from "@nestjs/common";
import { PaginationQueryDto } from "./dto/pagination-query.dto";

@Controller("items")
export class ItemsController {
  @Get()
  findAll(@Query() query: PaginationQueryDto) {
    // query.page and query.limit are guaranteed to be number types
    return {
      pageType: typeof query.page,
      limitType: typeof query.limit,
      ...query,
    };
  }
}
```

If a client requests `GET /items?limit=10&page=2`, the `enableImplicitConversion: true` option automatically transforms the string query parameters into numeric values:

```json
// GET /items?limit=10&page=2
// Response: 200 OK
{
  "pageType": "number",
  "limitType": "number",
  "page": 2,
  "limit": 10
}
```

If a client sends an invalid non-numeric string (e.g., `GET /items?limit=abc`), the implicit conversion fails to parse it as an integer, and the `@IsInt()` validator triggers a standard bad request error response:

```json
// GET /items?limit=abc
// Response: 400 Bad Request
{
  "statusCode": 400,
  "message": [
    "limit must be an integer number"
  ],
  "error": "Bad Request"
}
```

    ```json
      "lastName": "Lovelace"
    }
    ```

    Response:
    ```json
    // Response: 201 Created
    {
      "fullName": "Ada Lovelace"
    }
    ```

## Validation groups

Same DTO, different routes:

```typescript title="dto/user.dto.ts"
import { IsEmail, IsOptional, IsString, MinLength } from "class-validator";

export class UserDto {
  @IsEmail({}, { groups: ["create", "update"] })
  email: string;

  @IsString({ groups: ["create"] })
  @MinLength(8, { groups: ["create"] })
  @IsOptional({ groups: ["update"] })
  password?: string;
}
```

```typescript title="users.controller.ts"
import { Body, Controller, Patch, Post, UsePipes, ValidationPipe } from "@nestjs/common";
import { UserDto } from "./dto/user.dto";

@Controller("users")
export class UsersController {
  @Post()
  @UsePipes(new ValidationPipe({ groups: ["create"], whitelist: true }))
  create(@Body() dto: UserDto) {
    return dto;
  }

  @Patch(":id")
  @UsePipes(new ValidationPipe({ groups: ["update"], whitelist: true }))
  update(@Body() dto: UserDto) {
    return dto;
  }
}
```

Request to create a user without a password:

```json
// POST /users
{
  "email": "a@b.c"
}
```

Because the `create` group requires a password, the validation pipe rejects the request:

```json
// Response: 400 Bad Request
{
  "statusCode": 400,
  "message": [
    "password must be longer than or equal to 8 characters",
    "password must be a string"
  ],
  "error": "Bad Request"
}
```

Request to update the user (where the `update` validation group designates the password as optional):

```json
// PATCH /users/1
{
  "email": "a@b.c"
}
```

```json
// Response: 200 OK
{
  "email": "a@b.c"
}
```

## Nested arrays

Decorators do not recurse without `@ValidateNested()` and `@Type()` from `class-transformer`:

```typescript title="create-order.dto.ts"
import { Type } from "class-transformer";
import { IsArray, IsString, ValidateNested } from "class-validator";

export class OrderItemDto {
  @IsString()
  sku: string;
}

export class CreateOrderDto {
  @IsArray()
  @ValidateNested({ each: true })
  @Type(() => OrderItemDto)
  items: OrderItemDto[];
}
```

If we send an invalid nested item payload:

```json
{
  "items": [
    { "sku": "A100" },
    { "sku": 123 }
  ]
}
```

The pipe automatically traverses the array and throws a nested path error:

```json
{
  "statusCode": 400,
  "message": [
    "items.1.sku must be a string"
  ],
  "error": "Bad Request"
}
```

## Custom error shape

To return clean, standardized validation details (e.g. mapping internal validator constraints to a friendly list of fields), customize the `exceptionFactory` in `main.ts`:

```typescript title="main.ts" ins={4,11-19}
import "reflect-metadata";
import { NestFactory } from "@nestjs/core";
import { BadRequestException, ValidationPipe } from "@nestjs/common";
import { ValidationError } from "class-validator";
import { AppModule } from "./app.module";

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  app.useGlobalPipes(
    new ValidationPipe({
      exceptionFactory: (errors: ValidationError[]) =>
        new BadRequestException({
          statusCode: 400,
          error: "Validation failed",
          details: errors.map((e) => ({
            field: e.property,
            messages: Object.values(e.constraints ?? {}),
          })),
        }),
    })
  );
  await app.listen(3000);
}
bootstrap();
```

```http
// Invalid Request Payload:
POST /users HTTP/1.1
Content-Type: application/json

{

  "password": "short"
}

// Custom 400 Response (Using exceptionFactory map):
HTTP/1.1 400 Bad Request
Content-Type: application/json

{
  "statusCode": 400,
  "error": "Validation failed",
  "details": [

      "messages": ["email must be an email"]
    },

      "field": "password",
```

## Custom asynchronous validation with Dependency Injection

Often, validation requires checking state outside the payload (e.g., verifying database uniqueness before executing an insert, see [[nestjs/data/typeorm/postgresql-setup|TypeORM setup]] for database configuration).

### 1. Define the custom validator and constraint
Create a custom constraint class that implements `ValidatorConstraintInterface` and is decorated with `@Injectable()`. This allows the NestJS container to resolve any injected service or DB connection (like Prisma/TypeORM):

```typescript title="is-unique.validator.ts" collapse={1-9}
import { Injectable } from "@nestjs/common";
import { 
  registerDecorator, 
  ValidationOptions, 
  ValidatorConstraint, 
  ValidatorConstraintInterface,
  ValidationArguments 
} from "class-validator";
import { DataSource } from "typeorm";

@ValidatorConstraint({ name: "IsUniqueConstraint", async: true })
@Injectable()
export class IsUniqueConstraint implements ValidatorConstraintInterface {
  constructor(private readonly dataSource: DataSource) {}

  async validate(value: any, args: ValidationArguments): Promise<boolean> {
    const [tableName, columnName] = args.constraints as [string, string];
    const repository = this.dataSource.getRepository(tableName);
    
    // Check if any record already exists with the given column value
    const entity = await repository.findOne({ where: { [columnName]: value } });
    return !entity; // returns true if the value is unique (does not exist)
  }

  defaultMessage(args: ValidationArguments): string {
    return `${args.property} must be unique. The value is already registered.`;
  }
}

// Decorator definition function
export function IsUnique(tableAndColumn: [string, string], validationOptions?: ValidationOptions) {
  return function (object: object, propertyName: string) {
    registerDecorator({
      target: object.constructor,
      propertyName: propertyName,
      options: validationOptions,
      constraints: tableAndColumn,
      validator: IsUniqueConstraint,
    });
  };
}
```

<Aside type="caution" title="Register custom constraints in Module Providers">

Since `IsUniqueConstraint` is decorated with `@Injectable()`, you **must** register it in your module's `providers` array (e.g., in `users.module.ts`), otherwise NestJS will fail to resolve the class dependencies during injection:

```typescript title="users.module.ts"
import { Module } from "@nestjs/common";
import { TypeOrmModule } from "@nestjs/typeorm";
import { User } from "./entities/user.entity";
import { UsersController } from "./users.controller";
import { UsersService } from "./users.service";
import { IsUniqueConstraint } from "./is-unique.validator";

@Module({
  imports: [TypeOrmModule.forFeature([User])],
  controllers: [UsersController],
  providers: [UsersService, IsUniqueConstraint], // <-- Register custom validator here!
})
export class UsersModule {}
```

</Aside>

Add your custom decorator to your DTO fields:

```typescript title="create-user.dto.ts"
import { IsEmail, IsNotEmpty } from "class-validator";
import { IsUnique } from "./is-unique.validator";

export class CreateUserDto {
  @IsNotEmpty()
  @IsEmail()
  @IsUnique(["users", "email"])
  email: string;
}
```

### 3. Bind the NestJS DI container in `main.ts`
By default, `class-validator` instantiates custom validation constraint classes using `new`, bypassing the NestJS DI container. This makes database repository injection crash on startup with a dependency resolution error:

```text
Error: Nest can't resolve dependencies of the IsUniqueConstraint (?, ...). Please make sure that the argument DataSource at index [0] is available in the UsersModule context.
```

Bind the class-validator engine to the NestJS container in `main.ts` using `useContainer` to resolve constraints correctly:

```typescript title="main.ts" ins={3,8-9}
import "reflect-metadata";
import { NestFactory } from "@nestjs/core";
import { useContainer } from "class-validator";
import { AppModule } from "./app.module";

async function bootstrap() {
  const app = await NestFactory.create(AppModule);
  
  // Bind class-validator to the NestJS container, enabling DI in custom constraints
  useContainer(app.select(AppModule), { fallbackOnErrors: true });
  
  await app.listen(3000);
}
bootstrap();
```

<Aside type="caution" title="The race-condition vulnerability">

Asynchronous custom validators are non-atomic. Two concurrent API requests with the exact same email can validate concurrently, pass the database uniqueness check, and both proceed to write, resulting in a duplicate DB error. **Always** back custom validators with a unique index (`UNIQUE`) inside the physical database schema to ensure absolute atomicity.

</Aside>

### 4. The container-leak test suite hang gotcha

In [[nestjs/recipes/testing|testing]] environments (Jest/Vitest/Bun), calling `useContainer` binds validation constraints to the compiled `TestingModule` container. If you do not reset this reference during test teardowns, **the entire compiled application container remains in memory**. This triggers major memory leaks and prevents the runner process from exiting, hanging CI pipelines indefinitely with Jest's open handles warning:

```text
Jest did not exit one second after the test run has completed.
This usually means that there are asynchronous operations that weren't stopped in your tests. Consider running Jest with `--detectOpenHandles` to troubleshoot this issue.
```

**Resolution**: Always reset `useContainer(null)` in the E2E test teardown:

```typescript title="users.e2e.spec.ts" collapse={1-5} ins={17}
import { describe, beforeAll, afterAll } from "@jest/globals";
import { INestApplication } from "@nestjs/common";
import { Test, TestingModule } from "@nestjs/testing";
import { useContainer } from "class-validator";
import { AppModule } from "../src/app.module";

describe("Users (E2E)", () => {
  let app: INestApplication;

  beforeAll(async () => {
    const moduleFixture: TestingModule = await Test.createTestingModule({
      imports: [AppModule],
    }).compile();

    app = moduleFixture.createNestApplication();
    
    // Bind container for tests
    useContainer(app.select(AppModule), { fallbackOnErrors: true });
    
    await app.init();
  });

  afterAll(async () => {
    // 1. Reset container to prevent memory leaks and hung runners!
    useContainer(null);
    
    // 2. Safely close application
    await app.close();
  });
});
```

## High-volume validation performance: Event loop blocking

Standard NestJS validation pipes execute **synchronously** when parsing and transforming. If your application handles bulk file records or highly nested arrays (e.g., validating a JSON spreadsheet upload with 10,000 recursive sub-objects):
1. The heavy nested validation recurses synchronously on the CPU.
2. The single-threaded Node.js event loop is completely blocked for several hundred milliseconds.
3. All other concurrent requests stall, driving up LCP and request latency.

### Mitigation Strategies

- **Validate in chunks**: Chop massive arrays into small batches (e.g. processing batches of 100) and execute validation iteratively with `setImmediate` or `setTimeout` breaks to yield CPU back to the event loop.
- **Microservice offloading**: Offload validation to an isolated worker thread or a secondary microservice using NestJS queues (RabbitMQ/BullMQ).
- **Fast validation schemas**: For performance-critical bulk operations, bypass `class-validator` completely and use highly optimized schema libraries like **TypeBox** or **Zod** within custom validation pipes to execute validation up to 10x faster.

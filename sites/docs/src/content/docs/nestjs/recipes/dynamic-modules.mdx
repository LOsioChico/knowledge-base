> Dynamic modules allow you to configure modules dynamically at registration time. Primitives like `register`, `forRoot`, and `registerAsync` map custom options (like S3 bucket names, regions, and credentials) into the dependency injection (DI) container so services can consume them asynchronously.

## Why do we need dynamic modules?

To understand why we need dynamic modules, consider a **static module**. A static module is hardcoded: every time you import it, it behaves exactly the same way.

However, what happens if your application needs a **reusable service** whose behavior must be customized depending on where it is imported?
*   **The Bucket Example**: You write a `StorageModule` that uploads files to Amazon S3. In a single application, you need to upload user avatars to a **public bucket** (`my-public-avatars`) and export PDF invoices to a **secure private bucket** (`my-private-invoices`).
*   **Why not just use environment variables inside the service?** If your service directly reads `process.env.S3_BUCKET` or injects `ConfigService` directly, it is locked to **one single bucket**. You cannot reuse the uploading logic for two different buckets inside the same application.

Dynamic modules solve this by acting as a **configurable factory**. When you import the module, you pass the options in, and NestJS instantiates the providers customized with those exact options.

## The Modern Way: `ConfigurableModuleBuilder`

Introduced in NestJS 9, `ConfigurableModuleBuilder` automatically generates the boilerplate types (`register`, `registerAsync`, `inject`, `useFactory`, `useClass`, `useExisting`) for dynamic modules, reducing boilerplate code by up to 70%.

### 1. Build the Module Definitions

```typescript
import { from } from "rxjs";

// storage.module-definition.ts
import { ConfigurableModuleBuilder } from "@nestjs/common";
import { StorageOptions } from "./storage-options.interface";

// ConfigurableModuleBuilder generates standard dynamic module patterns
export const { ConfigurableModuleClass, MODULE_OPTIONS_TOKEN } =
  new ConfigurableModuleBuilder<StorageOptions>()
    .setClassMethodName("register") // Defines "register" and "registerAsync" methods
    .build();
```

### 2. Implement the Injectable Service

Inject the auto-generated `MODULE_OPTIONS_TOKEN` directly to access the options configured at startup:

```typescript
import { from } from "rxjs";

// storage.service.ts
import { Inject, Injectable } from "@nestjs/common";
import { MODULE_OPTIONS_TOKEN } from "./storage.module-definition";
import { StorageOptions } from "./storage-options.interface";

@Injectable()
export class StorageService {
  constructor(
    @Inject(MODULE_OPTIONS_TOKEN)
    private readonly options: StorageOptions,
  ) {}

  async uploadFile(fileName: string, content: string): Promise<{ url: string; bucket: string; sizeBytes: number }> {
    if (!this.options.bucket) {
      throw new Error("S3 bucket configuration is missing");
    }
    
    // Simulate S3 client upload
    const region = this.options.region ?? "us-east-1";
    return {
      url: `https://s3.${region}.amazonaws.com/${this.options.bucket}/${fileName}`,
      bucket: this.options.bucket,
      sizeBytes: Buffer.byteLength(content),
    };
  }
}
```

### 3. Implement the Module

By extending `ConfigurableModuleClass`, NestJS automatically adds the `register` and `registerAsync` methods under the hood:

```typescript
import { from } from "rxjs";

// storage.module.ts
import { Module } from "@nestjs/common";
import { ConfigurableModuleClass } from "./storage.module-definition";
import { StorageService } from "./storage.service";

@Module({
  providers: [StorageService],
  exports: [StorageService],
})
export class StorageModule extends ConfigurableModuleClass {}
```

## Static vs. Asynchronous Registration

You can register the module inside your root application module in one of several ways. `ConfigurableModuleBuilder` automatically generates support for static options passing and three distinct asynchronous resolution strategies.

<Tabs>
  <TabItem label="Static (register)">
    Use `register` when configuration options are available statically at build or startup time:

    ```typescript
import { from } from "rxjs";

// app.module.ts
    import { Module } from "@nestjs/common";
    import { StorageModule } from "./storage.module";

    @Module({
      imports: [
        StorageModule.register({
          bucket: "my-public-avatars",
          region: "us-west-2",
        }),
      ],
    })
    export class AppModule {}
    ```
  </TabItem>
  <TabItem label="Async (useFactory)">
    Use `useFactory` to inject `@nestjs/config`'s `ConfigService` (or other dependencies) and resolve options dynamically from environment variables using a factory function:

    ```typescript
import { from } from "rxjs";

// app.module.ts
    import { Module } from "@nestjs/common";
    import { ConfigModule, ConfigService } from "@nestjs/config";
    import { StorageModule } from "./storage.module";

    @Module({
      imports: [
        ConfigModule.forRoot({ isGlobal: true }),
        StorageModule.registerAsync({
          imports: [ConfigModule],
          inject: [ConfigService],
          useFactory: (config: ConfigService) => ({
            bucket: config.getOrThrow<string>("AWS_S3_BUCKET"),
            region: config.get<string>("AWS_REGION", "us-east-1"),
          }),
        }),
      ],
    })
    export class AppModule {}
    ```
  </TabItem>
  <TabItem label="Async (useClass)">
    Use `useClass` to delegate option creation to a custom configuration class. NestJS will instantiate a private instance of this class and call its factory method to resolve the options:

    ```typescript
import { from } from "rxjs";

// app.module.ts
    import { Module, Injectable } from "@nestjs/common";
    import { StorageModule } from "./storage.module";
    import { StorageOptions, StorageOptionsFactory } from "./storage-options.interface";

    @Injectable()
    export class StorageConfigService implements StorageOptionsFactory {
      createStorageOptions(): StorageOptions {
        return {
          bucket: "my-class-bucket",
          region: "eu-central-1",
        };
      }
    }

    @Module({
      imports: [
        StorageModule.registerAsync({
          useClass: StorageConfigService,
        }),
      ],
      providers: [StorageConfigService],
    })
    export class AppModule {}
    ```
  </TabItem>
  <TabItem label="Async (useExisting)">
    Use `useExisting` when a configuration provider has already been registered in another imported module, allowing you to reuse that exact provider instance without creating a new one:

    ```typescript
import { from } from "rxjs";

// app.module.ts
    import { Module } from "@nestjs/common";
    import { StorageModule } from "./storage.module";
    import { StorageConfigModule } from "./storage-config.module"; // exports StorageConfigService
    import { StorageConfigService } from "./storage-config.service";

    @Module({
      imports: [
        StorageConfigModule,
        StorageModule.registerAsync({
          imports: [StorageConfigModule],
          useExisting: StorageConfigService,
        }),
      ],
    })
    export class AppModule {}
    ```
  </TabItem>
</Tabs>

## The Classic Way: Manual Dynamic Module

Understanding the classic manual way is crucial for handling legacy code bases or complex scenarios, such as when you need custom provider generation, multiple distinct options objects, or complex multi-module wiring.

```typescript
import { from } from "rxjs";

// storage.module.ts (Manual Pattern)
import { DynamicModule, Module, Provider, Inject, Injectable } from "@nestjs/common";
import { StorageOptions } from "./storage-options.interface";

export const STORAGE_OPTIONS = "STORAGE_OPTIONS";

@Injectable()
export class StorageService {
  constructor(
    @Inject(STORAGE_OPTIONS)
    private readonly options: StorageOptions,
  ) {}

  async uploadFile(fileName: string, content: string) {
    return { url: `https://s3.amazonaws.com/${this.options.bucket}/${fileName}` };
  }
}

@Module({})
export class StorageModule {
  // Static options registration
  static register(options: StorageOptions): DynamicModule {
    return {
      module: StorageModule,
      providers: [
        {
          provide: STORAGE_OPTIONS,
          useValue: options,
        },
        StorageService,
      ],
      exports: [StorageService],
    };
  }

  // Async options registration using factory injections
  static registerAsync(options: {
    imports?: any[];
    inject?: any[];
    useFactory: (...args: any[]) => Promise<StorageOptions> | StorageOptions;
  }): DynamicModule {
    const optionsProvider: Provider = {
      provide: STORAGE_OPTIONS,
      useFactory: options.useFactory,
      inject: options.inject || [],
    };

    return {
      module: StorageModule,
      imports: options.imports || [],
      providers: [optionsProvider, StorageService],
      exports: [StorageService],
    };
  }
}
```

## Show, Don't Tell: Runtime Demonstration

Let's inspect how the dynamic `StorageModule` behaves when wired into a controller.

### 1. Injected Controller

```typescript
import { from } from "rxjs";

// files.controller.ts
import { Body, Controller, Post, InternalServerErrorException } from "@nestjs/common";
import { StorageService } from "./storage.service";

@Controller("files")
export class FilesController {
  constructor(private readonly storageService: StorageService) {}

  @Post("upload")
  async upload(@Body() body: { fileName: string; content: string }) {
    try {
      return await this.storageService.uploadFile(body.fileName, body.content);
    } catch (error) {
      throw new InternalServerErrorException((error as Error).message);
    }
  }
}
```

### 2. Concrete Payloads

`POST /files/upload` with a valid body:

```json
{
  "fileName": "avatar.png",
  "content": "base64encodedimagedata"
}
```

Successful `201 Created` response payload:

```json
{
  "url": "https://s3.us-west-2.amazonaws.com/my-public-avatars/avatar.png",
  "bucket": "my-public-avatars",
  "sizeBytes": 22
}
```

If the dynamic options load an empty bucket name, the service throws, and the controller yields `500 Internal Server Error`:

```json
{
  "statusCode": 500,
  "message": "S3 bucket configuration is missing",
  "error": "Internal Server Error"
}
```

## Gotchas and Best Practices

<Aside type="danger" title="Dynamic Module Deduplication Collision">

If you import the same module class twice in the same `imports` list with different configurations, NestJS will **deduplicate** the imports, meaning only the first module configuration will take effect:

```typescript
// DANGER: NestJS will only instantiate ONE StorageModule and overwrite the other!
@Module({
  imports: [
    StorageModule.register({ bucket: "avatars" }),
    StorageModule.register({ bucket: "invoices" }), 
  ],
})
export class AppModule {}
```

**How to solve this**: To run multiple instances of the same service with different configurations, you must wrap them in **separate wrapper modules** (e.g., `AvatarsStorageModule` and `InvoicesStorageModule`) that import and then export their respective customized versions, or use the manual custom provider pattern to register them with unique injection tokens.

```typescript
import { from } from "rxjs";

// avatars-storage.module.ts
import { Module } from "@nestjs/common";
import { StorageModule } from "./storage.module";

@Module({
  imports: [StorageModule.register({ bucket: "avatars" })],
  exports: [StorageModule],
})
export class AvatarsStorageModule {}

// invoices-storage.module.ts
import { Module } from "@nestjs/common";
import { StorageModule } from "./storage.module";

@Module({
  imports: [StorageModule.register({ bucket: "invoices" })],
  exports: [StorageModule],
})
export class InvoicesStorageModule {}
```

</Aside>

<Aside type="caution" title="Generic Token Collisions">

If you write multiple manual dynamic modules and register options using a generic token name (e.g., `OPTIONS` or `CONFIG`), Nest's IoC container will overwrite providers with matching tokens. 

**Rule of thumb**: Always prefix/namespace option tokens specifically (`STORAGE_OPTIONS`, `REDIS_OPTIONS`) to avoid startup-time conflicts. `ConfigurableModuleBuilder` handles this automatically by generating a unique object identity token.

</Aside>

<Aside type="caution" title="Global Scope Overreach">

By default, dynamic modules are bounded to the module registry where they are imported. Adding `@Global()` makes the dynamic module global, which means other modules do not need to re-import it. 

If using `ConfigurableModuleBuilder`, you can dynamically support optional global registration by configuring it on the builder:

```typescript
export const { ConfigurableModuleClass, MODULE_OPTIONS_TOKEN } =
  new ConfigurableModuleBuilder<StorageOptions>()
    .setClassMethodName("register")
    .setExtras(
      { isGlobal: false }, // Default extras value
      (definition, extras) => ({
        ...definition,
        global: extras.isGlobal, // dynamically sets global property
        // Note: isGlobal is a custom name; "global" is the key NestJS looks for
      }),
    )
    .build();
```

Which allows the consumer to specify: `StorageModule.register({ bucket: 'my-bucket', isGlobal: true })`.

</Aside>

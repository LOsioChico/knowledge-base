> AWS Secrets Manager stores small named blobs (DB credentials, API tokens) encrypted under a [[aws/kms|KMS]] key, exposed via `GetSecretValue` so applications never ship credentials in env files.

Before diving into Secrets Manager, make sure you understand:
- [[aws/cli/profiles-and-credentials|AWS Profiles & Credentials]]: since reading AWS secrets requires authenticating requests via IAM identities and AWS credentials.

## Mental model

A **secret** is name + versioned value (≤64 KB) + KMS key reference. Versions are immutable with stages (`AWSCURRENT`, `AWSPREVIOUS`, `AWSPENDING` during rotation).

Access control layers:

- **[[aws/iam|IAM]] identity policy** on the caller (`secretsmanager:GetSecretValue` on the secret ARN).
- **Resource policy** on the secret (required for cross-account).
- **KMS key policy**: reading a secret requires `kms:Decrypt` on the encryption key.

## Secret ARNs end in a six-character random suffix

```
arn:aws:secretsmanager:us-east-2:111122223333:secret:MySecret-nutBrk
                                                     ^^^^^^^^ ^^^^^^
                                                     name     random suffix
```

AWS appends `-XXXXXX` so ARNs stay unique across delete/recreate ([source](https://docs.aws.amazon.com/secretsmanager/latest/userguide/troubleshoot.html)).

<Aside type="caution" title="Use wildcard suffix in IAM policies">

Pinning the exact ARN breaks when the secret is recreated. Use `arn:...:secret:db/prod/admin-*` not the full suffix.

</Aside>

Partial-ARN lookups fail when the secret name itself ends in `-abcdef`: pass the full ARN or the bare name ([source](https://docs.aws.amazon.com/secretsmanager/latest/userguide/troubleshoot.html)).

## Cross-account access needs three policies

All three must agree ([source](https://docs.aws.amazon.com/secretsmanager/latest/userguide/auth-and-access_examples_cross.html)):

| Policy | Lives in (profile) | Allows |
| --- | --- | --- |
| Resource policy on secret | `account-a` | `GetSecretValue` for `account-b` principal |
| Key policy on KMS key | `account-a` | `kms:Decrypt` + `kms:DescribeKey` for `account-b` |
| Identity policy on caller | `account-b` | `GetSecretValue` + `kms:Decrypt` on ARNs |

Convention matches [[aws/account-migrations|account migrations]]: `account-a` (source), `account-b` (target).

<Aside type="caution" title="Cross-account requires customer-managed KMS">

Default `aws/secretsmanager` AWS-managed key cannot be used cross-account. Fix at create time: re-encrypt later means a new secret ([source](https://docs.aws.amazon.com/secretsmanager/latest/userguide/auth-and-access_examples_cross.html)). Same pattern as [[aws/kms|KMS cross-account]].

</Aside>

## Multi-consumer secrets

Prefer **one secret per consumer + credential** even when values match: minimal IAM scope, independent rotation, auditable "who can read this?" by name.

## Operational defaults

- **Customer-managed KMS key at create** (~$1/month): option to share cross-account later.
- **Hierarchical names** (`prod/orders-db/admin`); IAM on prefix wildcards.
- **`name-*` in IAM**, never exact ARN with suffix.
- **Tag `Owner` and `Environment`** for cost and access reviews.
- **Enable rotation only with a tested [[aws/lambda|Lambda]] rotator** for that credential type.

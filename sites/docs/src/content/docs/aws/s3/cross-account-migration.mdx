> Move a bucket between accounts by recreating config in the target, granting cross-account read on the source, and using `aws s3 sync` for server-side copies.

Before diving in, make sure you understand:
- [[aws/s3/quickstart|S3 quickstart]]: since cross-account bucket migrations require a working knowledge of bucket primitives and safe bucket defaults.

## Trade-off vs replication

[S3 replication](https://docs.aws.amazon.com/AmazonS3/latest/userguide/replication.html) fits ongoing sync. For a one-shot migration before cutover, `aws s3 sync` is simpler: re-run to catch up during the window.

## Recipe

<ShellSession
  vars={[
    { name: "ACCOUNT_B_ID", placeholder: "444455556666" },
    { name: "SRC_BUCKET", placeholder: "my-source-bucket" },
    { name: "DST_BUCKET", placeholder: "my-dest-bucket" },
  ]}
/>

Profiles: `account-a` (source), `account-b` (target). Set once (same pattern as [[aws/rds/cross-account-snapshot|RDS cross-account snapshot]] exports):

```bash
export ACCOUNT_B_ID=$ACCOUNT_B_ID
export SRC_BUCKET=$SRC_BUCKET
export DST_BUCKET=$DST_BUCKET
```

Use `"$SRC_BUCKET"` / `"$DST_BUCKET"` in commands and `${ACCOUNT_B_ID}` inside heredocs below.

## 1. Pre-flight

Mixing profiles is the expensive mistake: the next writes land in whatever account the profile resolves to. Run [`aws sts get-caller-identity`](https://docs.aws.amazon.com/cli/latest/reference/sts/get-caller-identity.html) per profile and confirm `Account` matches the source and target you intend:

```bash
aws sts get-caller-identity --profile account-a --output json
aws sts get-caller-identity --profile account-b --output json
```

Expected output for the source and target account profiles:

```json
// Output for --profile account-a:
{
    "UserId": "AROA111122223333:session-name",
    "Account": "111122223333",
    "Arn": "arn:aws:sts::111122223333:assumed-role/MigrationRole/session-name"
}

// Output for --profile account-b:
{
    "UserId": "AROA444455556666:session-name",
    "Account": "444455556666",
    "Arn": "arn:aws:sts::444455556666:assumed-role/MigrationRole/session-name"
}
```

## 2. Inventory the source bucket

You will recreate every setting on the destination bucket; defaults are not always what you want. Capture policy, encryption, versioning, and a baseline object count (match this after sync):

```bash
aws s3api head-bucket            --profile account-a --bucket "$SRC_BUCKET"
aws s3api get-bucket-location    --profile account-a --bucket "$SRC_BUCKET"
aws s3api get-bucket-policy      --profile account-a --bucket "$SRC_BUCKET" --query Policy --output text > src-bucket-policy.json
aws s3api get-bucket-encryption  --profile account-a --bucket "$SRC_BUCKET" > src-bucket-encryption.json
aws s3api get-bucket-versioning  --profile account-a --bucket "$SRC_BUCKET"
aws s3api get-public-access-block --profile account-a --bucket "$SRC_BUCKET"
aws s3 ls                        --profile account-a s3://$SRC_BUCKET --recursive --summarize | tail -2
```

Expected baseline object count stdout (e.g. 15,240 objects):
```text
   Total Objects: 15240
      Total Size: 1073741824
```

## 3. Create destination in `account-b`

Create the bucket in the target Region, then apply the same defensive defaults the source used (public access block, versioning, encryption):

```bash
aws s3api create-bucket \
  --profile account-b --region us-east-1 \
  --bucket "$DST_BUCKET"
# For regions other than us-east-1, add:
#   --create-bucket-configuration LocationConstraint=<REGION>

aws s3api put-public-access-block \
  --profile account-b --bucket "$DST_BUCKET" \
  --public-access-block-configuration BlockPublicAcls=true,IgnorePublicAcls=true,BlockPublicPolicy=true,RestrictPublicBuckets=true

aws s3api put-bucket-versioning \
  --profile account-b --bucket "$DST_BUCKET" \
  --versioning-configuration Status=Enabled

aws s3api put-bucket-encryption \
  --profile account-b --bucket "$DST_BUCKET" \
  --server-side-encryption-configuration '{"Rules":[{"ApplyServerSideEncryptionByDefault":{"SSEAlgorithm":"AES256"}}]}'
```

If the source uses SSE-KMS with a customer-managed key (CMK), replicate or share the key: same pattern as [[aws/rds/cross-account-snapshot|RDS cross-account snapshot]].

## 4. Grant `account-b` read on source

`aws s3 sync` from `s3://src` to `s3://dst` runs as account B's principal but reads account A's bucket. Merge this statement into the existing bucket policy (do not overwrite blindly; you saved `src-bucket-policy.json` in step 2). Write the grant file with shell-expanded placeholders:

```bash
cat > src-bucket-grant.json <<EOF
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "AllowAccountBToReadForMigration",
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::${ACCOUNT_B_ID}:root" },
      "Action": ["s3:GetObject", "s3:GetObjectVersion", "s3:ListBucket"],
      "Resource": ["arn:aws:s3:::${SRC_BUCKET}", "arn:aws:s3:::${SRC_BUCKET}/*"]
    }
  ]
}
EOF
```

Merge the grant into the saved policy using `jq`, then apply the updated policy to the source bucket using `put-bucket-policy`:

```bash
jq -s '.[0].Statement += .[1].Statement | .[0]' \
  src-bucket-policy.json src-bucket-grant.json > src-bucket-policy-merged.json

aws s3api put-bucket-policy \
  --profile account-a --bucket "$SRC_BUCKET" \
  --policy file://src-bucket-policy-merged.json
```

The `put-bucket-policy` command prints no success body (silently succeeds with empty stdout). Re-run `get-bucket-policy` if you need to confirm the merged statement is present, or verify the silent success exit:

```text
// Command outputs nothing on success:
$ aws s3api put-bucket-policy --profile account-a --bucket "$SRC_BUCKET" --policy file://src-bucket-policy-merged.json
$ 
```

For SSE-KMS objects, also grant `account-b` `kms:Decrypt` on the source CMK ([[aws/kms|KMS]] key policy, same idea as the RDS recipe).

## 5. Sync

Server-side copy from source to destination; re-run the same command at cutover to catch objects written since the first pass:

```bash
aws s3 sync \
  --profile account-b \
  "s3://$SRC_BUCKET" \
  "s3://$DST_BUCKET"
```

Expected sync stdout trace with progress and file metrics:

```text
copy: s3://my-source-bucket/assets/logo.png to s3://my-dest-bucket/assets/logo.png
copy: s3://my-source-bucket/documents/report.pdf to s3://my-dest-bucket/documents/report.pdf
copy: s3://my-source-bucket/index.html to s3://my-dest-bucket/index.html
Completed 3 part(s) with ~15.2 MiB/s (13 objs left)
```

For very large buckets, run from EC2 in the destination Region so client bandwidth is not the bottleneck.

## 6. Verify

Compare object counts on both buckets; they should match when the sync finished cleanly:

```bash
aws s3 ls --profile account-a s3://$SRC_BUCKET --recursive --summarize | tail -2
aws s3 ls --profile account-b s3://$DST_BUCKET --recursive --summarize | tail -2
```

Expected output confirming matching counts (e.g., 15,240 objects in both):
```text
Source Bucket (Account A):
   Total Objects: 15240
      Total Size: 1073741824

Destination Bucket (Account B):
   Total Objects: 15240
      Total Size: 1073741824
```

## 7. Cut writers over

Point applications at `$DST_BUCKET`, run a final sync, and keep the source bucket read-only for a rollback window.

## Cleanup

Restore `src-bucket-policy.json` from step 2 when migration is done; eventually empty and delete the source bucket.

<Aside type="caution" title="Do not skip">
- **Recreate bucket policy** in target: copy source, then audit principals.
- **Enable versioning before sync** if the source had it.
- **Public-access block** at account and bucket level.
</Aside>

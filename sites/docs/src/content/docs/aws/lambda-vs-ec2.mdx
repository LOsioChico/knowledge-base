> [[aws/lambda|Lambda]], [[aws/ec2|EC2]], and [[aws/ecs|Fargate]] solve different workload shapes. Picking Lambda for a long-lived backend trades cold starts, connection-pool overhead, and per-request pricing that crosses always-on compute well before "high traffic".

## TL;DR

- **Lambda**: event glue, low-duty cron, spiky webhooks, scale-to-zero.
- **Fargate**: long-running containers without Lambda's request model.
- **EC2**: sustained backends, GPUs, lift-and-shift, predictable cost at high utilization.
- **Pricing crossover**: ~50 req/s × 200 ms × 512 MB Lambda ≈ **8×** cost of `m7g.medium` 24/7 ([math below](#pricing-math-one-concrete-workload)).
- **Lambda monolith failure mode**: cold starts, RDS Proxy tax, 15 min cap, no long-lived WebSockets on the function itself.

## Decision matrix

| Dimension | Lambda | Fargate | EC2 |
| --- | --- | --- | --- |
| Unit | Function | Container task | VM |
| Scale-to-zero | Yes | No | No |
| Max execution | **15 min** ([source](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)) | Unlimited | Unlimited |
| Cold start | Under 100 ms to 1+ s ([source](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html#cold-start-latency)) | Tens of seconds | Minutes |
| Persistent connections | No (use RDS Proxy) | Yes | Yes |
| WebSockets on compute | No (API GW WebSocket) | Yes | Yes |
| Pricing | Per req + GB-s | Per vCPU-s + GB-s | Per instance-hour |
| Sync payload cap | **6 MB** sync ([source](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html)) | None | None |

## Where Lambda wins

- **Event-driven glue**: S3 → resize, DynamoDB [[effect-ts/streams|stream]] → notify, EventBridge enrichers.
- **Low-duty cron**: 30 s/day job ≈ $0 Lambda vs ~$8/mo idle `t3.micro` ([EC2 pricing](https://aws.amazon.com/ec2/pricing/on-demand/)).
- **Spiky webhooks**: GitHub/Stripe callbacks.
- **Per-tenant isolation** at scale-to-zero per tenant.

## Where Lambda hurts a long-lived backend

### Cold starts + warming anti-patterns

Heavy Init (NestJS, Spring) pushes toward 1 s+ cold starts. **Provisioned [[effect-ts/concurrency|Concurrency]]** bills ~$54/mo for 10 × 512 MB reserved envs before invocations ([Lambda pricing](https://aws.amazon.com/lambda/pricing/)). **SnapStart** helps Java/Python/.NET Init: not universal.

Unblessed 5-minute ping keeps **one** env warm: second concurrent request still cold-starts.

### DB connections → RDS Proxy

200 concurrent Lambdas → 200 DB connections. [RDS Proxy](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/rds-proxy.html) pools connections: ~$43/mo on 4-vCPU `db.r5.xlarge` ([pricing](https://pricing.us-east-1.amazonaws.com/offers/v1.0/aws/AmazonRDS/current/us-east-1/index.json)).

### Hard limits

- **900 s timeout**: long jobs need Step Functions, durable functions, or Fargate/EC2.
- **6 MB sync response**: stream via S3 [[aws/s3/presigned-urls|presigned URLs]] or response streaming.
- **No long-lived sockets** on Function URL: API Gateway WebSocket or other compute.

<Aside type="note" title="Durable Functions change the model">

Can run up to one year with checkpoints ([source](https://docs.aws.amazon.com/lambda/latest/dg/durable-functions.html)): different SDK contract, not "timeout lifted".

</Aside>

## Where Fargate is the honest middle

Docker locally = prod Docker; persistent connections; WebSockets; ~$15/mo for 0.5 vCPU / 1 GB task ([Fargate pricing](https://aws.amazon.com/fargate/pricing/)). What you want when tempted by Lambda "for ops simplicity" on a sustained API.

## Where EC2 still wins

Sustained throughput, WebSocket scale, GPU/custom kernel, Reserved/Savings Plans discounts, lift-and-shift unchanged.

## Pricing math: one concrete workload

Workload: **50 req/s sustained**, **200 ms**, **512 MB**, ~129.6M req/mo (us-east-1 on-demand, verify before quoting):

**Lambda (x86)**:

- Requests: 129.6M × $0.20/M = **$25.92**
- Compute: 12.96M GB-s × $0.0000166667 = **$216.00**
- ≈ **$235/mo** (+ RDS Proxy if needed)

**EC2 `m7g.medium`**: $0.0408/hr × 720 hr ≈ **$29.38/mo**

**Fargate 1 vCPU / 2 GB**: ≈ **$35.55/mo**

Lambda ≈ **8×** `m7g.medium` at this shape. Crossover with `m7g.medium` near **~6 req/s** with same per-invocation params.

<Aside type="caution" title="Re-do the math for your shape">

Lambda cost is linear in requests × memory × duration; EC2 is flat per hour. Use [AWS pricing calculator](https://calculator.aws/).

</Aside>

## Decision shortcuts

<Tabs>
  <TabItem label="Quick checks">
    1. Work &gt; 15 min per invocation? → Fargate/EC2 (or Step Functions).
    2. Discrete event trigger (S3, SQS, schedule)? → Lambda likely fits.
    3. Sustained [[effect-ts/platform|HTTP]] API north of ~5–10 req/s? → Run pricing math.
    4. WebSockets or &gt;6 MB responses? → Not Lambda.
    5. Team needs local/prod parity? → Fargate/EC2.
    6. "Don't want to manage instances"? → Fargate, not Lambda-by-default.
  </TabItem>
</Tabs>

## Common gotchas shoehorning a backend into Lambda

<Aside type="caution" title="Provisioned Concurrency does not eliminate scale-out cold starts">

N+1th concurrent request still cold-starts unless you size PC to peak: approaching always-on cost ([PC docs](https://docs.aws.amazon.com/lambda/latest/dg/provisioned-concurrency.html)).

</Aside>

<Aside type="caution" title="Init IAM failures look like latency spikes">

Missing permission during static init fails Init, resets environment ([runtime lifecycle](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtime-environment.html#runtimes-lifecycle-init-errors)).

</Aside>

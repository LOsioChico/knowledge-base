> Schema is the runtime boundary layer for `Effect<A, E, R>` programs: it checks unknown input, derives TypeScript types from the same declaration, and encapsulates parse failures inside the typed `E` error channel.

---

## The Boundary Problem

In standard TypeScript, `JSON.parse` returns `any`, and casting it with `as Todo` only changes what the compiler believes at compile time. It does not perform any runtime checks on the actual data shape.

```ts twoslash
interface Todo {
  readonly id: number;
  readonly title: string;
  readonly completed: boolean;
}

const raw = '{"id":"1","title":"Write docs"}';
const todo = JSON.parse(raw) as Todo;

console.log(todo.id + 1);
// Prints "11" at runtime because the ID was actually a string!

console.log(todo.completed);
// Prints undefined because the completed property was missing!
```

This code type-checks perfectly, but it fails silently at runtime. `Schema` puts the validation check directly at the boundary, ensuring that malformed payloads are rejected immediately before they propagate deeper into your application logic.

---

## Effect Schema vs. Zod

While Zod is an industry-standard validation library, `Effect Schema` is designed from the ground up for functional composition and tight integration with the Effect ecosystem.

| Dimension | Zod | Effect Schema |
| --- | --- | --- |
| **Design Paradigm** | Imperative, builder-pattern based fluent API. | Functional, declarative, combinator-based compositional API. |
| **Type Parity** | Derived TS types are separate: can drift on complex transformations or custom checks. | 100% type-safe compile-time/runtime parity: derives exact `Type` and `Encoded` types from the same tree. |
| **Error Channel** | Throws raw `ZodError` or returns `{ success: false, error }` object structure. | Integrated directly into Effect's typed error channel as `ParseResult.ParseError` inside `Effect<A, ParseError>`. |
| **Transformations** | `.transform()` allows arbitrary mutations but type-inference hides the original wire shape. | Dual-channel transformations (`Schema.transform`) preserve both `Encoded` (input) and `Type` (output) schemas, ensuring full bidirectional capability. |
| **Performance** | Standard runtime evaluation with average overhead. | Highly optimized code-generation: compiles schemas into hyper-fast specialized JS functions at runtime. |

## 1. Declare the Schema

Use `Schema.Struct` to build an object schema from field schemas. Primitive schemas use PascalCase names like `Schema.String`, `Schema.Number`, and `Schema.Boolean`.

```ts twoslash
import { Schema } from "effect";

const Todo = Schema.Struct({
  id: Schema.Number,
  title: Schema.String,
  completed: Schema.Boolean,
});
```

---

## 2. Infer the TypeScript Types

Instead of duplicating declarations by writing an `interface` manually, you can extract the derived type directly from your runtime schema using `Schema.Schema.Type`:

```ts twoslash
import { Schema } from "effect";

const Todo = Schema.Struct({
  id: Schema.Number,
  title: Schema.String,
  completed: Schema.Boolean,
});

// Extract the decoded TypeScript type
type Todo = Schema.Schema.Type<typeof Todo>;

const validTodo: Todo = {
  id: 1,
  title: "Write docs",
  completed: false,
};
```

---

## 3. Bidirectional Transformations

Unlike typical parsers, `Schema` models transformations that preserve both the raw wire shape and the clean domain shape. `Schema.Schema.Encoded` extracts the raw input shape, while `Schema.Schema.Type` extracts the output shape.

```ts twoslash
import { Schema } from "effect";

const User = Schema.Struct({
  id: Schema.NumberFromString, // Transforms string -> number
  name: Schema.String,
});

type User = Schema.Schema.Type<typeof User>;
// Resolved type: { readonly id: number; readonly name: string; }

type UserEncoded = Schema.Schema.Encoded<typeof User>;
// Resolved type: { readonly id: string; readonly name: string; }
```

### Custom Transformations

You can write custom, bidirectional mappings using `Schema.transform()`. This function accepts an input schema, an output schema, and mapping functions for decoding and encoding:

```ts twoslash
import { Schema } from "effect";

// Custom transformation: trims leading and trailing whitespaces from a string
const TrimmedString = Schema.transform(
  Schema.String,
  Schema.String,
  {
    decode: (str) => str.trim(),
    encode: (str) => str,
  }
);

const UserProfile = Schema.Struct({
  username: TrimmedString,
});
```

## 4. Decode Inbound Payloads

Use `Schema.decodeUnknown(schema)(input)` to parse untrusted data (like `JSON.parse` outputs or network response bodies). This returns an `Effect` that succeeds with the validated domain type, or fails with a structured `ParseResult.ParseError` in the error channel.

```ts twoslash
import { Effect, Schema } from "effect";

const Todo = Schema.Struct({
  id: Schema.Number,
  title: Schema.String,
  completed: Schema.Boolean,
});

const untrustedInput: unknown = {
  id: 1,
  title: "Write docs",
  completed: false,
};

const program = Schema.decodeUnknown(Todo)(untrustedInput);

// Run the program synchronously
const result = Effect.runSync(program);
console.log(result);
// Prints: { id: 1, title: 'Write docs', completed: false }
```

## 5. Domain Error Mapping

Raw parse errors are extremely useful for debugging, but you should map them to clean, domain-specific tagged errors before they cross your internal application layer. Use `ParseResult.TreeFormatter.formatErrorSync` to turn a `ParseError` into a highly readable hierarchical diagnostic message.

```ts twoslash
import { Data, Effect, ParseResult, Schema } from "effect";

// Define a custom, tagged domain error
class ParseFailure extends Data.TaggedError("ParseFailure")<{
  readonly issues: string;
}> {}

const Todo = Schema.Struct({
  id: Schema.Number,
  title: Schema.String,
  completed: Schema.Boolean,
});

type Todo = Schema.Schema.Type<typeof Todo>;

const parseTodo = (input: unknown): Effect.Effect<Todo, ParseFailure> =>
  Schema.decodeUnknown(Todo)(input).pipe(
    Effect.mapError(
      (parseError) =>
        new ParseFailure({
          issues: ParseResult.TreeFormatter.formatErrorSync(parseError),
        }),
    ),
  );
```

If we pass invalid data, the formatted error output clearly highlights the failing nested fields:

```typescript
const badInput: unknown = {
  id: "not-a-number",
  title: "Write docs",
};

const result = Effect.runSyncExit(parseTodo(badInput));
// Failure(ParseFailure: { readonly id: number; readonly title: string; readonly completed: boolean }
// ├─ ["id"]
// │  └─ Expected number, actual "not-a-number"
// └─ ["completed"]
//    └─ is missing)
```

## Gotchas and Best Practices

<Aside type="danger" title="Do not runSync on untrusted boundaries directly">

`Effect.runSync` will throw a native `FiberFailure` exception if the underlying effect fails. Because `decodeUnknown` can fail when given invalid data, executing `runSync` without handling the error first will crash the process. Use `Effect.runSyncExit` or handle/map the error using operations like `catchTag` before execution.

</Aside>

<Aside type="caution" title="Validate at the boundary only">

Parse your incoming network payloads or configuration objects once at the entry point of your module or service. Once the data is proven valid, propagate the clean, inferred TypeScript type (`Todo`) throughout the rest of your inner domain services instead of re-parsing the same values recursively.

</Aside>
